# 供暖与制冷独立计算范围设计

## 1. 目标

在能耗页面第三步增加两个独立计算范围开关：

- 参与供暖计算；
- 参与制冷计算。

两项可以单独启用或同时启用，但不能同时关闭。未启用的一侧不计算年度热需求、分项需求或等效峰值，也不计入设备用能和全年总用电。

## 2. 用户界面

第三步“空调与供暖设备系统”顶部增加“冷热计算范围”区域，默认同时启用供暖和制冷，以兼容新建项目的既有行为。

关闭某一侧后：

- 对应系统类型、室内设定温度、季节性能系数和室外设计温度控件禁用；
- 另一侧及照明、设备、新风、生活热水参数保持可用；
- 两项都关闭时，页面阻止提交并提示至少选择一种计算。

## 3. 数据契约

前端请求增加：

```json
{
  "calculate_heating": true,
  "calculate_cooling": true
}
```

后端归一化后保存：

```json
{
  "heating": {"enabled": true},
  "cooling": {"enabled": true}
}
```

后端校验两个值必须是布尔语义，且至少一个为 `true`。`enabled` 是计算范围的唯一权威字段；设备 `system_type` 只描述已启用侧采用的系统形式。

## 4. 计算行为

共同的几何、围护和年度运行输入仍可归一化，但输出按范围门控：

- 供暖关闭：所有供暖热需求分项、供暖总需求和供暖等效峰值返回 `null`，供暖设备用能为 `0`；
- 制冷关闭：所有制冷热需求分项、制冷总需求和制冷等效峰值返回 `null`，制冷设备用电为 `0`；
- 开启侧保持现有 HDD/CDD 计算；
- 风机、照明、插座设备和生活热水继续按当前规则计算；
- 总用电只汇总已启用侧的冷热设备用能及其他直接用电。

返回结果增加：

```json
{
  "calculation_scope": {
    "heating": true,
    "cooling": false
  }
}
```

使用 `null` 表示“未计算/不适用”，避免用数值零表示物理负荷恰好为零。

## 5. 结果展示

未启用侧的年度需求、分项需求和峰值显示：

```text
未启用（本报告不计算制冷）
```

设备用能表保留该行并显示 `0 kWh/a`，名称后注明“未启用”，使总用电构成可核查。已启用侧继续显示数值。

## 6. 历史报告兼容

- 新报告读取 `heating.enabled` 和 `cooling.enabled`；
- 老报告缺少 `enabled` 时，根据对应 `system_type != "none"` 推断；
- 更旧的扁平参数根据 `heating_system`、`cooling_system` 推断；
- 如果老报告连系统字段也不存在，保持旧行为：供暖和制冷均启用；
- 历史报告加载后，第三步开关和控件禁用状态必须同步。

## 7. 与未来逐小时气象的关系

本次开关定义建筑是否存在对应服务范围。未来逐小时模型只在已启用侧，根据逐小时气象、室内设定温度、内部得热和建筑热平衡判断具体供暖或制冷时段。计算范围与逐时运行判断保持分离。

## 8. 测试与验收

必须覆盖：

1. 仅供暖时制冷需求和峰值为 `null`，制冷用电为 0；
2. 仅制冷时供暖侧同理；
3. 冷热同时启用时保持当前数值；
4. 两侧同时关闭时后端拒绝请求；
5. 前端存在两个独立开关、禁用逻辑和至少选择一项的校验；
6. 历史报告缺少 `enabled` 时按系统类型恢复；
7. 结果页把未启用侧显示为“不计算”，不显示为零负荷；
8. 文化宫四层关闭制冷后，制冷设备用电不进入总用电。

## 9. 约束

- 本次不增加独立供暖面积或制冷面积字段；
- 本次不实现逐小时气象或动态热模型；
- 不修改既有围护结构输入方式；
- 不暂存、提交、推送或部署。
