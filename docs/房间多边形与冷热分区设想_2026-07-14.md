# 房间多边形与冷热分区设想

更新日期：2026-07-14

## 当前决定

本设想暂不实施。当前优先级是先把现有建筑的设计冷、热负荷计算和设备选型完整跑通，确认输入、公式、结果和校核流程可用后，再继续设计房间多边形与冷热分区功能。

本阶段不修改图像识别、房间提取、区域选择或页面交互。

## 设想背景

网站后续应将制冷和制热作为两套相互独立的计算与设备选型流程：

- 制冷计算只读取空调区，输出设计冷负荷并进行制冷设备选型；
- 制热计算只读取供暖区，输出设计热负荷并进行制热设备或供暖末端选型；
- 同一房间可以同时供冷、供暖，也可以仅供暖、仅供冷或均不启用；
- 空调面积、供暖面积和整层建筑面积不得继续共用一个面积字段。

盐湖区工人文化宫案例说明了这种拆分的必要性：原冷负荷计算主要覆盖一层部分空调房间，而四层在原设计中只有供暖、没有供冷。若直接按整层面积计算制冷负荷，会得到不符合原设计范围的结果。

## 核心设想

当前图像模型识别墙、窗、门。后续可在识别结果之上提取由墙体围合的室内空白区域，将其转换为可选择的房间多边形。

建议流程：

1. 识别墙、窗、门；
2. 对墙体断点和门洞进行拓扑修补；
3. 从墙体之间的空白区域提取闭合空间；
4. 为每个闭合空间生成稳定的房间编号和多边形；
5. 在平面图上显示可点击的房间覆盖层；
6. 用户选择各房间是否制冷、是否供暖；
7. 分别汇总空调面积和供暖面积；
8. 冷负荷模块只读取制冷区域，热负荷模块只读取供暖区域。

## 推荐交互

- 默认一个闭合多边形对应一个房间；
- 点击房间后高亮，并显示房间编号、名称和面积；
- 支持多选相邻房间并合并为一个计算区域；
- 支持拆分错误区域或手工补画多边形；
- 支持将楼梯、电梯、设备井等区域标记为“忽略”；
- 支持“一键选择整层供暖”；
- 制冷区域仍由用户逐房间选择或批量选择；
- 页面始终显示整层建筑面积、空调面积、供暖面积和未分配面积，避免口径混淆。

每个房间后续可进一步设置：

- 房间名称和房间类型；
- 是否制冷、是否供暖；
- 使用面积和层高；
- 人数与人员活动状态；
- 新风量；
- 照明功率和设备功率；
- 使用时间表；
- 夏季、冬季室内设计温湿度；
- 与室外、相邻房间、屋面、地面等边界的关系。

```json
  "floor_id": "floor_04",

  "room_type": "rehearsal_hall",

  "height_m": 4.5,
  "heating_enabled": true,
  "cooling_enabled": false,
  "ignored": false,
  "source": "auto_with_manual_review"

```

房间数据应与识别结果一同持久化，并记录模型版本、原图尺寸、比例尺、人工修改记录和更新时间，供后续计算直接复用。

## 不能直接把墙体轮廓当作房间的原因

模型输出的墙体轮廓通常表示墙体自身的像素区域，不是室内使用空间。房间应从墙体之间的自由空间提取。此外还需要处理：

- 门洞使墙体边界不闭合；
- 分割结果存在像素级断点；
- 墙体类别同时包含内墙和外墙；
- 文字、柱子和家具可能错误切割空间；
- 大厅可能被分成多个区域；
- 相邻房间可能因墙体漏识别而连成一个区域；
- 楼梯间、设备井等闭合区域不一定属于冷热负荷计算区域。

因此推荐采用“自动提取 + 人工确认和修正”，不将自动闭合作为唯一依据。

## 与现有问题的关系

该设想后续可以帮助解决：

- 空调面积、供暖面积和整层面积混用；
- 缺少逐层、逐房间计算对象；
- AI 识别结果没有在后续计算中复用；
- 不能表示全楼供暖、部分房间制冷；
- 不能为不同房间配置人员、新风、照明、设备和使用时间；
- 无法把设备选型结果追溯到具体服务区域。

## 恢复开发前置条件

满足以下条件后再恢复该功能设计：

1. 设计冷负荷模块能够完成一次完整计算；
2. 设计热负荷模块能够完成一次完整计算；
3. 制冷和制热设备选型已拆分；
4. 已用文化宫原计算书完成总量和主要分项校核；
5. 已明确房间级负荷模块需要的最小输入字段；
6. 已确定识别结果的持久化格式和版本失效规则。

## 后续实施建议

恢复开发时，先用一张结构清晰、房间数量较少的单层平面图验证以下最小闭环：

1. 自动提取房间多边形；
2. 用户点击选择供冷或供暖区域；
3. 保存并重新加载选择结果；
4. 正确汇总空调面积和供暖面积；
5. 将选择结果传入已经验证过的冷、热负荷模块。

小样验证通过后，再增加区域合并、拆分、手工补画和房间参数配置。
