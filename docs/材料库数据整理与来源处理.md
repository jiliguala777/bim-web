# 材料库数据整理与来源处理

本文档保存 BIM Web 围护结构材料库的数据来源、原始报告保护规则、分类与
结构化工具、历史处理进度以及正式入库路线。

> 本文中的 `E:\...` 路径和批次数字是 2026 年 7 月工作环境的历史记录，
> 不属于程序运行时必需配置。平台当前读取的正式材料库位于仓库
> `data/envelope_databases/`。

## 1. 材料库在平台中的作用

BIM Web 在图纸识别和建筑几何确认后，需要为负荷和年度能耗计算选择围护
结构热工参数。网页通过 `energy_library.py` 读取 SQLite 数据库，并提供：

- 基层外墙和外墙外保温系统；
- 外窗传热系数与太阳得热系数；
- 屋面、地面/楼板和外门传热系数；
- 遮阳系数；
- 地面接触类型；
- 外窗气密性。

正式数据库目录：

```text
data/envelope_databases/
```

主要数据库：

| 数据库 | 主要内容 |
|---|---|
| `wall_insulation.db` | 外墙外保温系统、热阻、传热系数、导热系数及来源证据 |
| `windows.db` | 外窗传热系数、太阳得热系数 |
| `exterior_wall.db` | 基层外墙 |
| `roof.db` | 屋面 |
| `floor.db` | 地面和楼板 |
| `door.db` | 外门 |
| `shading.db` | 遮阳和窗帘 |
| `floor_contact.db` | 地面接触类型及修正系数 |
| `window_air_tightness.db` | 外窗气密性 |

其中 `wall_insulation.db` 和 `windows.db` 已包含从检测报告抽取的真实数据；
其他库仍包含样例或人工补充数据，需要持续复核和完善。

## 2. 数据来源

### 2.1 自有检测报告

原始报告以 Word `.doc` 文件为主。处理过程包括：

1. 建立原始文件清单；
2. 排除封面、临时文件和低优先级内容；
3. 按围护结构、暖通和照明等大类筛选；
4. 对有用报告做细分类；
5. 抽取导热系数、传热系数、热阻等参数；
6. 保留报告编号、原始路径、原始结果和检测依据；
7. 经复核后导入正式 SQLite 库。

重点参数包括：

- 导热系数；
- 传热系数；
- 热阻；
- 太阳得热系数；
- 遮阳系数；
- 气密性等级。

### 2.2 网络公开资料

历史候选资料保存在本地外部数据目录，包括重庆、湘潭等公开发布的建筑节能
材料、门窗和幕墙热工参数。

网络资料通常先进入候选 CSV，完成来源、单位、适用对象和有效性复核后才能
进入正式数据库。网页下拉框中的可用值不能仅凭搜索摘要直接生成。

### 2.3 样例和人工补充数据

正式数据不足时，样例数据保证网页流程可以运行。样例必须保留来源标记，
后续应逐步由可追溯的真实数据替代。

## 6. 报告分类工具

历史分类程序位于：

```text
E:\shujuku\report_pipeline_v2
```

主要工具：

| 工具 | 职责 |
|---|---|
| `work_report_manifest.py` | 建立原始报告 manifest |
| `work_report_queue.py` | 建立主队列并排除封面、临时文件 |
| `content_screening.py` | 打开 Word 并按内容关键词分类 |
| `organize_files.py` | 将分类结果组织到派生目录 |
| `batch_screen_and_organize.py` | 筛选和组织批处理入口 |
| `batch_watchdog.py` | 卡死检测、跳过和恢复 |
| `useful_structuring.py` | 对有用报告做结构化 |

已知运行规则：

- 支持 `--source-root`，用于解析队列中的相对路径；
- 默认不在每个批次重复组织全部 skipped 文件；
- watchdog 等待子进程完整退出，不在 CSV 满行后提前终止组织阶段；
- 默认组织方式为 `copy`；
- `hardlink` 在历史环境中出现过 `OSError(22, 函数不正确。)`，不作为默认。

## 7. 历史批处理命令

以下命令用于说明当时的恢复方式，运行前必须根据当前进度调整 offset 和
limit：

```powershell
cd E:\shujuku
$env:PYTHONPATH="E:\shujuku"

python -m report_pipeline_v2.batch_watchdog `
  --queue E:\shujuku\output_experiment\work_report_queues\main_queue.csv `
  --offset 21100 `
  --limit 29727 `
  --skipped E:\shujuku\output_experiment\work_report_queues\skipped.csv `
  --organized-root E:\shujuku\organized_reports `
  --output-root E:\shujuku\output_experiment `
  --skip-sources E:\shujuku\output_experiment\skip_sources.txt `
  --log-dir E:\shujuku\output_experiment\logs `
  --source-root E:\shujuku\work_report
```

注意：

- `--source-root` 必须与队列相对路径的根目录一致；
- 默认使用复制模式；
- watchdog 会通过 `--resume` 继续批次；
- Word 卡死时会记录到 `skip_sources.txt` 并重启子进程；
- 重新运行前先确认是否已有完整输出，避免重复打开已处理报告。

## 9. 推荐的数据入库路线

1. 完成剩余报告的大类筛选；
2. 对新增 `useful/envelope` 做围护结构细分类；
3. 筛出确实包含热工参数的报告；
4. 结构化并保留原始证据；
5. 统一单位和字段含义；
6. 生成候选导入清单；
7. 人工抽样复核；
8. 备份当前正式数据库；
9. 使用对应导入工具更新 SQLite；
10. 运行材料库测试；
11. 在网页下拉框中验证名称、数值和单位；
12. 验证选中参数能正确进入设计负荷和年度能耗计算。

## 10. 入库质量要求

- 每条真实参数应尽量保留报告编号或公开来源；
- 保留原始结果文本，便于审计；
- 数值和单位必须分开存储；
- 不混淆材料导热系数、构造热阻和构件传热系数；
- 不将检测条件下的单项值无说明地当作完整构造参数；
- 重复数据应保留明确的去重规则；
- 样例数据和真实报告数据必须可区分；
- 修改正式数据库前必须备份；
- 更新后运行：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_envelope_libraries
.\.venv\Scripts\python.exe -m unittest tests.test_energy_template
```

## 11. 与平台发布的关系

正式材料库位于 GitHub 代码目录中，服务器路径为：

```text
/opt/bim-web/app/data/building_library.db
/opt/bim-web/app/data/envelope_databases/
```

材料库更新随代码提交进入 `origin/main`，服务器拉取后重启 `bim-web` 才会
加载新版本。更新 SQLite 前应备份服务器当前库；用户账号和上传结果位于
`/var/lib/bim-web`，与正式材料库分开。

材料研究原始文件、候选 CSV、大型报告和本地审计目录不进入 GitHub。
